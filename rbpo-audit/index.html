Блок 1 · Контекст

Композиционный анализ ПО (КАПО) — определение

Проект ГОСТ Р ЗИ КАПО · ТК 362, 2025 · §3 «Термины»
Что входит в КАПО
Управление составом ПО
  • Идентификация заимствованных компонентов (open-source + проприетарные + внутренние).
  • Формирование перечня программных компонентов (ППК / SBOM).
  • Анализ лицензий и юридической совместимости.
  • Контроль уязвимостей (CVE / БДУ ФСТЭК).
  • Контроль изменений между версиями продукта.
Что НЕ входит в КАПО — путают
Не задача SBOM-агрегатора
  • Статический анализ собственного кода — это SAST (SVACE, Coverity).
  • Динамический анализ — DAST.
  • Антивирусное сканирование — это §5.17, отдельная тема.
  • Reachability уязвимых методов — задача SAST с call-graph.
👉 КАПО — это управление составом ПО, а не качеством собственного кода. Это разные классы инструментов и разные ответственности.

ГОСТ §5.17 — проверка цепочки поставок на вредоносное ПО

§5.17 · стр. 35–37 · вне скоупа Сервиса
§5.17 шире SBOM и лицензий
  • Требует антивирусного сканирования компонентов цепочки поставок.
  • Требует контроля договоров с поставщиками компонентов.
  • Требует аудита инфраструктуры разработки соисполнителей.
  • Требует контроля целостности готовых бинарников — подписи, хэши.
  • Требует проверки репутации поставщиков (OSA, БДУ ФСТЭК).
Принципиальная позиция «§5.17 — другой класс инструментов: антивирус, infrastructure scanner, договорный контур. Сервис «РБПО-аудит» принципиально не закрывает §5.17 — это нужно говорить честно, чтобы не обещать регулятору невозможное».

Блок 3 · Почему задача сложная

Проблема №1: C/C++ legacy-сборки

Почему КАПО — нетривиальная задача в условиях МНТЦ МИЭТ
Кодовая база проекта
  • Основная задача МНТЦ МИЭТ — навести управляемость в сложном C/C++ продукте, не в типовом web/npm/maven-проекте.
  • Legacy-сборки: make, cmake, qmake, системные библиотеки, форкнутые компоненты.
  • Не все зависимости описаны в пакетных менеджерах (Conan и т.п.).
  • Широко используются статически линкованные внутренние библиотеки.
  • Главный критерий выбора инструмента: «кто лучше достаёт фактический состав C/C++ продукта», а не «кто красивее агрегирует».
Аналитическая справка AppSec vs CodeScoring «Не типовой web/npm/maven проект — большая часть кодовой базы на C/C++ с legacy-сборками. Нет универсального инструмента, который бы решил это автоматически».

Блок 3 · Почему задача сложная

Даже лидеры рынка осторожны: ограничения CodeScoring и AppSec

Проблема №2: технические ограничения коммерческих SCA-инструментов
Демонстрация 21.04.2026
CodeScoring
Сборочный контекст + eBPF
  • Анализ C/C++ через сборочный контекст + eBPF на Linux ядро ≥ 5.8.
  • Не видит статические зависимости и форки без явных метаданных.
  • Эвристика через сигнатуры — ~70% точности (помощь, не решение).
AppSec.Track
Требует Conan-манифеста
  • Для C/C++ требуется обязательный переход на Conan.
  • Часть соисполнителей МНТЦ МИЭТ это сделать пока не может.
  • Без Conan — нет манифеста — нет извлечения.
Цитата · встреча 21.04.2026 «Никакой готовый коммерческий инструмент не решает задачу exhaustive автоматического извлечения компонентов для такого продукта. Все доступные инструменты дают частичное покрытие и требуют либо preparatory работ, либо человеческого обогащения».
👉 Покупка одного инструмента задачу не решит. Нужна связка: внешние SCA-источники + внутренний приёмочный контур.

Блок 4 · Архитектурный ответ Сервиса

Pipeline обработки SBOM — от ZIP до единого CycloneDX

End-to-end автоматизация
  1. Соисполнитель формирует ZIP по канону
    YYYY/MM/DD/<contractor>/<component>/<archive>.zip
  2. ZIP содержит SBOM-Registry.xlsx (обязательно) + bom.json CycloneDX (provenance) + исходные SBOM-файлы соисполнителя.
  3. Оператор Общества загружает архив через веб-форму или REST API.
  4. Сервис парсит Excel, создаёт Component, Dependency, License.
  5. PURL-генерация для компонентов с известным ecosystem.
  6. Нормализация лицензий через SPDX List + choosealicense теги.
  7. Формирование единого CycloneDX 1.6 SBOM проекта по дате загрузки.
  8. Экспорт в Dependency Track через REST API.
Pipeline · схема
┌─ ZIP-архив соисполнителя ─────────────────┐ │ YYYY/MM/DD/<contractor>/<component>/ │ │ ├ SBOM-Registry.xlsx (обязат.) │ │ ├ bom.json (CycloneDX 1.6) (provenance)│ │ └ source/* (исходные SBOM) │ └───────────────────┬───────────────────────┘ ▼ Парсинг + нормализация │ ▼ PURL + SPDX + теги 5+8+4 │ ▼ Единый CycloneDX 1.6 проекта │ ┌───────────┴────────────┐ ▼ ▼ Dependency Track Юр. экспертиза (CVE-mapping) (вердикты юриста)

Блок 8 · Итог

Итог: что предлагается руководству

Решения, требуемые от руководства
  1. Продолжать развивать Сервис «РБПО-аудит» — он закрывает регламентную часть КАПО, лицензионный аудит и единый SBOM проекта.
  2. Не заявлять полное соответствие ГОСТ Р 56939-2024. Корректная формула: «закрывает ядро КАПО и является доказательным контуром для §5.16; §5.17 закрывается отдельными мерами».
  3. На ближайшие 30 дней — оформить регламент КАПО, утвердить формат сдачи SBOM соисполнителями, связать загрузки с релизными версиями, закрепить DT-отчёт как CVE-evidence.
Главный аргумент «Без Сервиса в условиях АО МНТЦ МИЭТ задача КАПО не решается ни закупкой одного коммерческого инструмента, ни передачей соисполнителям требований "делать у себя SBOM". Нужен централизованный приёмочный контроль с лицензионной экспертизой и журналом изменений».
Чек-лист решений руководства
  • Утвердить роль Сервиса как внутреннего корпоративного контура композиционного анализа.
  • Утвердить обязательную сдачу SBOM для всех соисполнителей.
  • Утвердить формат поставки (CycloneDX 1.6 + Excel-реестр).
  • Назначить владельца регламента КАПО организации.
  • Поддержать Phase 2 + Phase 3 дорожной карты.
