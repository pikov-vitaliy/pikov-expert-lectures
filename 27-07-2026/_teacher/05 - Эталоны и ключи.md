### Шаг 3.2 — разбор запроса

```sql
... WHERE label = 'Открыто' AND owner LIKE '%%' OR label LIKE '%%'
```

`AND` связывает сильнее, чем `OR`, поэтому выражение читается так:

```
(label = 'Открыто' AND owner LIKE '%%')  ИЛИ  (label LIKE '%%')
```

Второе слагаемое — `label LIKE '%%'` — истинно для любой строки, потому что `%` в LIKE означает «любая последовательность символов». Дизъюнкция с истиной даёт истину, и фильтр по грифу перестаёт что-либо значить.

Полезный дополнительный вопрос, если слушательница схватила быстро: «а что было бы, если бы условия стояли в другом порядке?» Ответ: ничего бы не изменилось — приоритет операций от порядка не зависит. Скобки вокруг всего условия ослабили бы конкретно эту атаку, но не устранили бы причину: данные всё равно остаются частью команды.

### Эталон Д3 — CWE-89

```python
sql = (
    "SELECT inv, kind, label, owner FROM media "
    "WHERE label = 'Открыто' AND owner LIKE ?"
)
return connection.execute(sql, (f"%{query}%",)).fetchall()
```

Типичная ошибка при исправлении: подстановка `?` вместе с процентами внутрь текста запроса — `LIKE '%?%'`. Так не работает: внутри строкового литерала `?` перестаёт быть параметром. Проценты должны быть в передаваемом значении, как в эталоне.

Вторая типичная ошибка — попытка обойтись экранированием кавычек. Разбирать её стоит подробно: это фильтрация по чёрному списку, она не полна и попутно ломает фамилии с апострофом.

### Эталон Д4 — CWE-22

```python
base = EXPORT_DIR.resolve()
candidate = (base / filename).resolve()
if not candidate.is_relative_to(base):
    raise ValueError(f"Имя файла {filename!r} выводит за пределы каталога выгрузки")
```

Обязательно `.resolve()` **и** у базы, и у кандидата: сравнение неканонических путей ненадёжно.

Типичная ошибка при исправлении: `if ".." in filename`. Разобрать, почему не годится — обратные слэши, процентное кодирование, символические ссылки, подкаталоги вида `a/../../b`. Правило: **проверяйте результат, а не текст**.

### Шаг 4.1 (проверено)

```
Ran 18 tests in 0.018s
OK
```

Через pytest — `18 passed, 11 subtests passed`.

### Шаг 4.2 — красное перед зелёным (проверено)

После замены импорта на `step3_defect`:

```
Ran 8 tests in 0.012s
FAILED (failures=6, errors=9)
```

Восемь тестовых методов дают 15 отказов, потому что два теста используют `subTest` и падают по нескольким наборам данных каждый. Это стоит отдельно проговорить: `subTest` показывает **все** несработавшие случаи, а не только первый.

### Эталон своих тестов (шаг 4.3)

```python
def test_search_for_unknown_owner_returns_nothing(self) -> None:
    rows = step3_fixed.find_public(self.connection, "Несуществующая")
    self.assertEqual(rows, [])

def test_confidential_records_never_appear_in_public_search(self) -> None:
    """Требование «никогда» № 1 с утренней доски, дословно."""
    for payload in ("Сидорова", "МНИ-003", "Кузнецов", "%"):
        with self.subTest(payload=payload):
            rows = step3_fixed.find_public(self.connection, payload)
            self.assertNotIn("Конфиденциально", {row[2] for row in rows})
```

Обязательно проговорить: второй тест — это дословный перевод требования, записанного утром на доске. Связь «требование через "никогда" → тест» и есть главный методический результат дня.

### Шаг 4.5 — ответ про quality gate

- **test** — всегда блокирующий. Красный тест означает, что программа делает не то, что заявлено.
- **sast** — блокирующий по находкам высокой критичности.
- **lint** — на старте внедрения можно сделать предупреждающим, но быстро переводят в блокирующий, иначе замечания копятся и обесцениваются.
- **sca** — часто начинают предупреждающим, потому что уязвимость в чужой библиотеке не всегда закрывается сегодня.

Ключевая мысль: конвейер без единого блокирующего шага — не конвейер, а генератор отчётов, которые перестают читать примерно через месяц.

**Ответ.** Неиспользуемая переменная `lines` в функции `export_report` файла `step3_defect.py` — та самая, которую находит ruff (правило F841). Список собирается и тут же выбрасывается.

Хороший переход к разговору о том, что автоматические проверки заменяют не мышление, а внимание, которого у человека конечное количество.

## Что делать, если задание 3 не пошло

Это единственное место дня, где реально можно застрять. Порядок действий по убыванию:

1. **Слушательница не понимает вывод программы.** Не переходите к коду. Вернитесь к выводу и разберите его построчно: сколько записей, какие грифы, сколько должно было быть.
2. **Понимает проблему, не видит строку в коде.** Дайте прямое указание на функцию, не на строку. Пусть найдёт сама внутри функции.
3. **Видит строку, не знает как исправить.** Отправьте к функции `connect` в том же файле — там `executemany` с `?` уже написан правильно. Приём «в вашем же файле есть готовый образец» работает лучше объяснения.
4. **Исправила, не работает.** Скорее всего `LIKE '%?%'` — разберите, почему `?` внутри строкового литерала перестаёт быть параметром.
5. **Прошло 25 минут, движения нет.** Переходите к совместному разбору: пишете вместе, вслух проговаривая каждый шаг. Оставшиеся Д4/Д1/Д2 после этого обычно идут самостоятельно — они проще.

Не оставляйте пару 4 незавершённой ради того, чтобы успеть пару 5. Пара 5 сокращается до 45 минут без потери смысла: тесты можно запустить готовые, свои не писать.
