Обратный контур: уязвимость из эксплуатации возвращается в разработку

Уязвимость, найденная при эксплуатации (5.22–5.24), должна вернуться назад: в реестр недостатков (5.5), в требования (5.3), архитектуру (5.6), модель угроз и поверхность атаки (5.7) — и затем пройти повторные проверки, приёмку (5.20) и поставку (5.21). Стандарт этот путь задумывает, но замыкает его не ссылками между пунктами, а событиями, которые разработчик сам прописывает в своих регламентах. Прямо по тексту: входная половина (5.22, 5.23, 5.24), повторный статический и динамический анализ после устранения (5.10.2.6, 5.11.2.6) и корректировка модели угроз, поверхности атаки и архитектуры по итогам нефункционального тестирования (5.19.2.5).

прямо в текстепо событиям разработчикапо номеру нет

1. Выявление

  • прямо 5.23.2.2«Осуществлять обработку поступающих запросов от пользователей (через службу технической поддержки, по иным каналам взаимодействия) с последующим анализом ошибок функционирования на предмет наличия уязвимостей (в случае получения таких запросов).»
  • прямо 5.24.2.2«Актуализировать информацию об уязвимостях ПО из открытых источников на регулярной основе на всем протяжении срока действия его технической поддержки: выполнять поиск в открытых источниках информации об уязвимостях самого ПО и его сторонних компонентов.»

2. Подтверждение и решение

  • прямо 5.23.2.4«Осуществлять анализ информации о найденных уязвимостях в ПО на предмет подтверждения наличия/отсутствия уязвимостей и принимать решение о необходимости их устранения по результатам оценки.»
  • прямо 5.23.2.5«Осуществлять оценку актуальности и критичности уязвимости с точки зрения безопасности ПО (в случае получения информации об уязвимости ПО из внешнего источника) и принимать решение о необходимости ее устранения по результатам оценки.»

3. Регистрация и контроль изменения

  • прямо 5.5.2.3«Контролировать реализацию изменений, связанных с недостатками ПО.»
  • прямо 5.5.2.4«Контролировать реализацию запросов на изменение в рамках жизненного цикла ПО.»
Передача подтверждённой уязвимости из 5.23 в реестр 5.5 по номеру не прописана.

4. Возврат в требования, архитектуру, модель угроз

  • по событиям 5.3.2.4«Осуществлять пересмотр набора требований безопасности на основе выполнения критериев пересмотра - с установленной периодичностью или при наступлении определенных событий.»
  • по событиям 5.6.2.4«Выполнять уточнение архитектуры ПО в процессе разработки кода и его изменений с установленной периодичностью или при наступлении определенных событий.»
  • по событиям 5.7.2.4«Выполнять уточнение модели угроз ПО для изменяемого в ходе разработки ПО кода с установленной периодичностью или при наступлении определенных событий.»
  • по событиям 5.7.2.5«Выполнять уточнение описания поверхности атаки для изменяемого в ходе разработки ПО кода с установленной периодичностью или при наступлении определенных событий.»
  • прямо 5.19.2.5«Осуществлять корректировку описания поверхности атаки, модели угроз и архитектуры ПО по результатам выполнения нефункционального тестирования.»
Эксплуатация как повод пересмотра не названа: события задаёт разработчик (5.3.3.1, 5.6.3.3). Перечень мер нейтрализации (5.7.3.2) в уточнение не входит.

5. Повторные проверки

  • прямо 5.10.2.5«Осуществлять пересмотр конфигурации и параметров настройки инструментов статического анализа при выполнении установленных событий (изменениях в правилах сборки, применяемых статических анализаторах, получении информации об уязвимостях и т.п.).»
  • прямо 5.10.2.6«Осуществлять повторный статический анализ ПО после устранения ранее выявленных ошибок и уязвимостей; внесения изменений в ходе разработки в исходные тексты ПО; изменения (для компилируемого в промежуточное используемых версий компиляторов, сред выполнения представление или интерпретируемого кода), обновлений используемых инструментов статического анализа.»
  • прямо 5.11.2.6«Проводить повторный динамический анализ модулей (компонентов) ПО с целью контроля устранения ошибок.»
  • прямо 5.16.2.3«Контролировать и актуализировать перечень зависимостей ПО в соответствии с регламентом композиционного анализа на предмет наличия известных уязвимостей.»
  • по событиям 5.18.3.1«… критерии выполнения повторного тестирования …»
  • по событиям 5.19.3.1«… критерии выбора версий ПО (модулей ПО, компонентов ПО), подлежащих нефункциональному тестированию, и определения периодичности тестирования …»
Экспертизу кода (5.9) и проверку на ВПО (5.17) повторять не требуется; проверки не ссылаются на уточнённые 5.6.3.4 и 5.7.3.5–5.7.3.7.

6. Приёмка исправления

  • прямо 5.20.2.2«Осуществлять анализ степени влияния на безопасность ПО неустраненных ошибок. Информация о неустраненных ошибках выпускаемого ПО должна быть зафиксирована (например, в системе управления изменениями, системе отслеживания ошибок и т.п.).»
Требования пропускать обновление через приёмку 5.20 по номеру нет.

7. Поставка и оповещение

  • прямо 5.21.3.1«… процедуры поставки ПО (обновлений ПО, включая обновления безопасности, предназначенных для устранения недостатков, в том числе уязвимостей) …»
  • прямо 5.22.2.3«Разработать процедуру оповещения пользователей о выпуске обновлений (включая обновления безопасности) и необходимости их установки.»
  • прямо 5.22.2.5«Разработать процедуру информирования пользователей ПО о выявленных уязвимостях и способах реализации мер по их нейтрализации до разработки обновлений безопасности, устраняющих уязвимость, по установленным каналам взаимодействия.»
Связка 5.20 → 5.21 по номеру не названа.
прописать

Что прописать в регламентах, чтобы контур замкнулся

  1. Включить «подтверждённую уязвимость из эксплуатации (5.23)» в события пересмотра требований (критерии 5.3.3.1), уточнения архитектуры (5.6.3.3), модели угроз и поверхности атаки (5.7.2.4, 5.7.2.5).
  2. Прописать передачу подтверждённой уязвимости в реестр недостатков и запросов на изменение (5.5.3.1, 5.5.3.3): идентификатор, версия, приоритет, статус.
  3. Обновлять вместе с моделью угроз и перечень мер нейтрализации (5.7.3.2) — в 5.7.2.4 и 5.7.2.5 он не входит.
  4. Добавить исправления уязвимостей в критерии повторного тестирования (5.18.3.1, 5.19.3.1); решить, нужны ли повторная экспертиза (5.9) и проверка на ВПО (5.17); проверки вести по уточнённым артефактам 5.6.3.4 и 5.7.3.5–5.7.3.7.
  5. Пропускать исправление через приёмку 5.20 (5.20.2.2) и поставку 5.21 (5.21.3.1); до выхода обновления — информировать пользователей о мерах нейтрализации (5.22.2.5).

Это выводы из текста стандарта: чего в нём нет по номерам пунктов. Для сертификации процессов безопасной разработки эти связки разработчик задаёт сам.

вопрос

Модель угроз и поверхность атаки (5.7)

Модель угроз (5.7.3.1) и описание поверхности атаки (5.7.3.3) явно используются в динамическом анализе (5.11), безопасности секретов (5.15), композиционном анализе (5.16), проверке на ВПО (5.17), функциональном и нефункциональном тестировании (5.18, 5.19), реагировании на уязвимости (5.23) и их поиске при эксплуатации (5.24). Динамический анализ получает ещё и перечень целей (5.7.3.4). Экспертиза кода (5.9) начинает с модулей поверхности атаки — связь без номера пункта.

источник

Архитектура (5.6) — самый частый источник

Описание архитектуры (5.6.3.2) нужно моделированию угроз, статическому и динамическому анализу; требования к принципам проектирования (5.6.3.1) — ещё семи процессам. Сама 5.6 строится на требованиях безопасности (5.3).

сток

Выпуск версии (5.20) собирает результаты проверок

Результаты экспертизы (5.9.3.2), отчёты SAST (5.10.3.4) и DAST (5.11.3.5), итоги устранения уязвимостей компонентов (5.16.3.5), отчёт функционального тестирования (5.18.3.2) и сведения о неустранённых недостатках из реестра 5.5.
