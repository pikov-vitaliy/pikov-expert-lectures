Матрица соответствия CodeScoring требованиям ТЗ OSA/SCA

Назначение Рабочая матрица для подготовки пилота. Сопоставляет требования ТЗ OSA/SCA/TQI с подтверждёнными возможностями CodeScoring. База анализа: ТЗ OSA‑SCA, материалы демонстрации поставщика, опросник и бюджетная оценка, публичная документация CodeScoring.

Это обезличенная рабочая выжимка. Любой статус «соответствует» по спорным пунктам не считается закрытым до демонстрации или письменного подтверждения поставщика.

Короткий вывод CodeScoring в целом соответствует базовой цели ТЗ: OSA/SCA, контроль цепочки поставки, анализ зависимостей, SBOM, политики, интеграция с GitLab/CI/CD и on‑premise поставка. Но соответствие нельзя признать полным и безусловным: часть языков из ТЗ не подтверждена как SCA‑экосистемы; OSA Proxy не покрывает весь список пакетных менеджеров; C/C++ без пакетного менеджера требует пилота на make/cmake/qmake и статической линковке; анализ готовых бинарников ограничен; требования к исполнителю (ФСТЭК, ISO 9001) не подтверждены представленными материалами.

Итоговый вердикт

Вопрос Вывод
Подходит ли CodeScoring под ТЗ? 🟡 Частично. Как кандидат для закупки/пилота — да; до признания полного соответствия нужно закрыть подтверждения и уточнить формулировки ТЗ.
Можно ли считать требования OSA/SCA закрытыми? 🔴 Нет. Большая часть закрывается, но есть рискованные пункты: OSA Firewall для всех пакетных менеджеров, qmake / C++ без пакетного менеджера, анализ готовых бинарников, языки Bash/Perl/SQL‑семейства, требования к исполнителю.
Главная рекомендация Пилот с приёмочными сценариями по спорным требованиям; в ТЗ разделить требования на: подтверждённые продуктом / требующие демонстрации / требующие договорной гарантии / уточняемые.

Главные разрывы и риски

5 зон, которые надо закрыть до признания соответствия Это смысловой центр анализа соответствия. Остальные таблицы — детализация.

# Требование / зона Что проверено Вывод
1 Языки из п. 3.3 ТЗ требует Java, Kotlin, JS, TS, Python, C, C++, Go, PHP, Ruby, C#, Objective‑C, Swift, Rust, Scala, Bash, Perl, SQL, PLSQL, PGSQL. Документация подтверждает широкий набор package/ecosystem‑сканирования, но не даёт явного подтверждения Bash, Perl, SQL/PLSQL/PGSQL как SCA‑экосистем. 🟡 Уточнить: SCA анализирует зависимости/пакеты, а не произвольный синтаксис всех языков.
2 OSA Firewall/Proxy для всех пакетных менеджеров Документация OSA Proxy явно указывает Maven, NPM, PyPI, NuGet V3, Go, Debian, Alpine/APK, RPM, Docker Registry. Conan/Conda/RubyGems — через плагины Nexus/JFrog, что не равно универсальному Proxy Firewall. 🔴 Риск. Если ТЗ требует именно Proxy‑перехват для Conan, Conda, RubyGems без Nexus/JFrog — не подтверждено.
3 C/C++ без пакетного менеджера: make, cmake, qmake Документация и материалы демонстрации подтверждают C/C++ build scan через агент/eBPF, GCC/Clang, CMake/Make. qmake прямо не подтверждён. Полнота инвентаризации достигается на этапе сборки. 🟡 Для qmake и конкретных сборок — демонстрация в пилоте.
4 Готовые бинарники и статическая линковка ТЗ требует binary analysis архивов и артефактов. Документация подтверждает сканирование архивных форматов. По подтверждённым материалам анализ уже собранных бинарников, особенно stripped и статически слинкованных, надёжно не решается. 🟡 Архивы/контейнеры — да; идентификация native binary/.a/.so без сборочного контекста — риск.
5 Требования к исполнителю ТЗ требует лицензию ФСТЭК на ТЗКИ/мониторинг ИБ, опыт 10 лет, ISO 9001, выделенное ИБ‑подразделение. В представленных материалах не подтверждено. 🔴 Запросить у поставщика/дистрибьютора подтверждающие документы.

Проверочные сценарии для пилота

Что прогнать на реальных сборках 1. On‑premise/Offline инсталляция в тестовом контуре; зафиксировать архитектуру: серверы, БД, сеть, доступы, обновление базы знаний. 2. Подключить GitLab + один CI/CD пайплайн C/C++ без Conan; build scan на make, cmake и отдельно qmake. 3. C/C++ статическая линковка: проект с .a/.so, stripped binary, внутренний форк; зафиксировать что видит автоматически, а что требует ручной разметки. 4. Conan flow: прямые/транзитивные зависимости, SBOM, граф, license/security policy. 5. OSA‑блокировка в фактическом режиме: через Nexus/JFrog plugin либо OSA Proxy. Отдельно Maven, NPM, NuGet, PyPI, Go, APT/RPM, Conan, Conda, RubyGems — если остаются обязательными. 6. SBOM export/import: CycloneDX JSON, SPDX JSON, CSV; совместимость с результатом стороннего OSS‑инструмента. 7. Уведомления: SMTP, Jira, UI events; audit log и отправка логов во внешнюю систему. 8. LDAP/AD или OIDC, RBAC, роли админ/ИБ/разработчик/наблюдатель. 9. Запросить документы: ФСТЭК, ISO 9001, опыт, структура ИБ‑подразделения.

Рекомендуемые уточнения ТЗ

  • Разделить SCA‑языки и package ecosystems — не требовать «анализ Bash/Perl/SQL» в одном списке с package ecosystems, если фактически нужен учёт зависимостей.
  • Разделить режимы: OSA Proxy / Nexus‑JFrog plugins / CLI‑agent. ТЗ сейчас смешивает их и может требовать от Proxy того, что покрывает только plugin/agent.
  • Явно описать C/C++ приёмку: make, cmake, qmake; GCC/Clang; Astra Linux; версия ядра; права eBPF; статическая линковка; внутренние библиотеки; ручная разметка.
  • Уточнить термин binary analysis: архивы/контейнеры отдельно, native stripped executables/.a/.so отдельно (последнее без сборочного контекста не гарантировано).
  • Для on‑premise/Offline выбрать один целевой вариант закупки.
  • Требования к исполнителю вынести в отдельный чек‑лист документов участника.
