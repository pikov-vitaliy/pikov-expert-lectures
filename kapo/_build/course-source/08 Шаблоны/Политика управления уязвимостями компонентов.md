# Политика управления уязвимостями компонентов

## Назначение
Политика устанавливает единые пороги severity, сроки устранения (SLA) и правила приоритизации уязвимостей в open source и сторонних компонентах продуктов Организации. Она отвечает на вопрос «нашли уязвимость в зависимости — что и в какой срок обязаны сделать».

## Когда применяется
- При появлении новых findings после прогона сервиса аудита/вердиктов поверх SBOM/VDR.
- При плановом пересмотре открытых уязвимостей (еженедельный triage).
- При публикации значимой уязвимости во внешних источниках (NVD, БДУ ФСТЭК) для компонента, входящего в портфель продуктов.

## Область действия и роли
| Параметр | Значение |
|---|---|
| На что распространяется | Все релизные сборки, контейнерные образы и поставки соисполнителей |
| Владелец политики | Руководитель направления безопасной разработки (роль, без ФИО) |
| Исполнитель triage | Дежурный аналитик SCA (роль) |
| Эскалация | Владелец продукта + комитет по риску |

## Классификация и пороги severity
Базовая метрика — CVSS v3.1/v4.0 базовый вектор, скорректированный по применимости (VEX) и по эксплуатируемости (EPSS, наличие в CISA KEV / актуальность по БДУ ФСТЭК).

| Severity | CVSS | Усиливающие факторы | SLA на устранение/митигацию |
|---|---|---|---|
| Critical | 9.0–10.0 | в KEV или EPSS ≥ 0.5, сетевой вектор без аутентификации | 7 календарных дней |
| High | 7.0–8.9 | достижима из недоверенной зоны | 30 дней |
| Medium | 4.0–6.9 | требует локального доступа/предусловий | 90 дней |
| Low | 0.1–3.9 | не достижима в продуктовой конфигурации | планово, следующий релиз |
| None / not affected | — | подтверждено VEX-статусом `not_affected` от ответственного issuer | фиксация обоснования и evidence, без работ |

> [!danger] Жёсткое правило gate
> Релиз с открытой Critical-уязвимостью без действующего исключения (см. [[Реестр исключений]]) не выпускается. CI security gate блокирует сборку.

## Порядок реакции (обязательный минимум)
1. Findings из сервиса аудита/вердиктов выгружаются как [[Порядок загрузки VDR из Dependency-Track|VDR]] и привязываются к версии компонента (PURL).
2. Каждая уязвимость получает VEX-статус: `affected` / `not_affected` / `under_investigation` / `fixed`; указывается issuer решения и evidence по продуктовой версии ([[02 Справочник/VEX в процессе РБПО - откуда берется и как выпускать|VEX в процессе РБПО]]).
3. Для `affected` заводится [[Паспорт риска компонента]] и назначается владелец с дедлайном по SLA.
4. Устранение: обновление версии, патч, замена компонента или компенсирующий контроль.
5. После исправления — обязательный [[Регламент ретеста после исправления|ретест]]; статус закрывается только по evidence.
6. Если SLA не выдерживается — оформляется [[Порядок принятия риска|принятие риска]] с ограниченным сроком.

## Что считается evidence закрытия
- VDR/VEX с новым статусом и ссылкой на сервис аудита/вердиктов.
- Diff версии компонента в SBOM (было/стало).
- Evidence для VEX: SBOM/ППК, build log, reachability/call graph, triage issue, upstream advisory/VEX как вспомогательный источник.
- Протокол ретеста с нулём подтверждённых эксплуатируемых findings по этой CVE/БДУ.
