# Билет 12

## Теоретический вопрос
Объясните, как динамическая зависимость C/C++ получает **координаты компонента**: от `.so`-файла из `DT_NEEDED` к системному пакету через `dpkg -S` / `apt`, что даёт имя пакета, версию и дистрибутив (DEB-координаты). Почему этот маппинг и есть ключевой шаг обогащения SBOM для legacy-C/C++? Что такое **unresolved library** — `.so`, который не разрешается ни в один установленный пакет, — и почему его нельзя ни выкинуть, ни выдать за разрешённый?

## Практический вопрос
> [!example] Мини-кейс
> После `readelf -d` получен список `NEEDED`-библиотек. Часть из них `dpkg -S` сопоставил с DEB-пакетами, а `libcustom.so.1` не нашёлся ни в одном пакете. Опишите, как оформить маппинг найденных, что занести в реестр unresolved и с каким confidence отдать спорные записи в сервис вердиктов.
>
> ```bash
> readelf -d ./app | grep NEEDED
> ldd ./app | awk '{print $3}' | grep -v '^$'
> dpkg -S /usr/lib/x86_64-linux-gnu/libssl.so.3   # → libssl3: ...
> dpkg -S /path/to/libcustom.so.1                  # → no path found ⇒ unresolved
> ```

## Что должен показать ответ
- **Источник факта**: `dpkg -S`/`apt` для ELF→DEB маппинга; для нерешённых — явная запись в реестр, а не молчаливый пропуск.
- **Инструмент**: `readelf -d`, `ldd`, `dpkg -S`; cdxgen для сборки обогащённого CycloneDX.
- **Владелец решения**: судьба unresolved-записей (доразметка, принятие, эскалация) — за сервисом аудита/вердиктов по политике.
- **Нормативная опора**: [[05 Нормативка/ГОСТ Р 56939-2024]], [[05 Нормативка/NIST SP 800-161 Rev.1]], [[05 Нормативка/BSI TR-03183-2 v2.1.0]].
- **Evidence**: таблица соответствия `.so`↔DEB-пакет; [[08 Шаблоны/Реестр unresolved libraries|реестр unresolved libraries]] с confidence.
