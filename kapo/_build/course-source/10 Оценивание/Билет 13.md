# Билет 13

## Теоретический вопрос
Что меняется в восстановлении состава C/C++, когда у проекта есть менеджер сборки — **Conan**, **vcpkg** — против голого `make`/`qmake`? Объясните, почему `conan graph info` даёт идентичность пакета (имя, версия, package_id, устойчивый PURL) и разрешённый граф, тогда как legacy `qmake`-проект с ручными `third_party/` каталогами идентичности не даёт. Почему наличие манифеста (`conanfile`, `vcpkg.json`) — это переход от «угадывания» к декларации, но private-qualifiers и внутренние remote всё ещё требуют аккуратной нормализации PURL?

## Практический вопрос
> [!example] Мини-кейс
> Два модуля одного продукта: один на Conan с `conanfile.txt`, другой — legacy на `qmake` с библиотеками, скопированными в `third_party/`. Опишите, как для первого получить идентичность и граф пакетов, а для второго — почему придётся опираться на ELF-анализ и ручную доразметку. Что сделать с private-qualifier в PURL, чтобы не утёк внутренний remote?
>
> ```bash
> conan graph info . --format=json     # идентичность + граф (package_id, версии)
> # qmake-проект: манифеста нет → состав восстанавливаем из сборки и ELF
> qmake -query QT_INSTALL_LIBS
> ```

## Что должен показать ответ
- **Источник факта**: `conan graph info` / `vcpkg` манифест как декларация состава; для qmake-legacy — сборка + ELF, не манифест.
- **Инструмент**: Conan/vcpkg для идентичности пакета; нормализация PURL с очисткой private-qualifiers.
- **Владелец решения**: трактовка legacy-модуля без манифеста и допуск private-remote — за специалистом композиционного анализа и сервисом вердиктов.
- **Нормативная опора**: [[05 Нормативка/ГОСТ Р 56939-2024]], [[05 Нормативка/OWASP SCVS]], [[05 Нормативка/NIST SP 800-218 SSDF]].
- **Evidence**: граф пакетов из `conan graph info`; нормализованные PURL без утечки внутренних remote.
