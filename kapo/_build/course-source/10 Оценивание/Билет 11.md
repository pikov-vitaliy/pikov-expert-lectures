# Билет 11

## Теоретический вопрос
Сравните **динамическую** и **статическую** линковку с точки зрения восстановления состава ПО. Почему динамическая зависимость (`.so`) видна и доказуема — через `DT_NEEDED` в ELF, `readelf -d`, `ldd`, — а статическая (`.a`) становится **слепой зоной**: компонент физически вшит в бинарь и исчезает из SBOM? Объясните, почему «сканер ничего не нашёл» для статически слинкованного бинаря — это не отсутствие зависимостей, а отсутствие доказательств.

## Практический вопрос
> [!example] Мини-кейс
> Дан один исполняемый файл. Нужно перечислить его сторонние компоненты. Снимите динамические зависимости и объясните, почему статически вшитая библиотека (например, своя сборка zlib через `.a`) в этот список не попадёт и что нужно сделать, чтобы её зафиксировать.
>
> ```bash
> readelf -d ./app | grep NEEDED      # динамика: DT_NEEDED
> ldd ./app                            # разрешённые .so
> # для .a-вшитого кода ELF-анализ молчит — нужен build-scan/LIEF
> ```

## Что должен показать ответ
- **Источник факта**: для динамики — `DT_NEEDED`/`readelf -d`/`ldd`; для статики — build evidence на этапе сборки (после линковки следов нет).
- **Инструмент**: `readelf`, `ldd`, LIEF для программного анализа ELF; cdxgen + build-scan для статики.
- **Владелец решения**: квалификация статической линковки как слепой зоны и постановка в worklist — за специалистом композиционного анализа.
- **Нормативная опора**: [[05 Нормативка/ГОСТ Р 56939-2024]], [[05 Нормативка/NIST SP 800-218 SSDF]] (PS.3.2), [[05 Нормативка/BSI TR-03183-2 v2.1.0]].
- **Evidence**: вывод `readelf -d` как occurrence; запись в [[08 Шаблоны/Реестр unresolved libraries|реестре unresolved/слепых зон]] для статики.
