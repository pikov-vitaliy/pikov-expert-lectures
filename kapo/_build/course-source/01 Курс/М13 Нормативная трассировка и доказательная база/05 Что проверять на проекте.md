# Что проверять на проекте: чек-лист аудитора по трассировке

Чек-лист для проверки доказательной базы композиционного анализа. Каждый пункт — проверяемое «да/нет» с указанием, какой артефакт смотреть.

- [ ] **Матрица трассировки существует и актуальна.** Есть живой документ `требование → практика → артефакт → владелец → место хранения`, а не разовый отчёт. Сверьте дату последнего обновления с датой последнего релиза ([[08 Шаблоны/Матрица evidence для аудита|шаблон]]).
- [ ] **Все пять требований КАПО покрыты строками.** Регламент, формирование ППК, контроль/актуализация, анализ на поверхности атаки, корректирующие воздействия — каждому соответствует хотя бы одна строка с артефактом ([[05 Нормативка/ГОСТ Р 56939-2024]], [[05 Нормативка/Проект ГОСТ Р КАПО]]).
- [ ] **Каждый артефакт привязан к версии продукта и релизу.** Нельзя предъявить SBOM «вообще» — только за конкретный commit/tag. Возьмите случайный релиз и попросите доказать выполнение одного требования за него.
- [ ] **SBOM конформен по полям BSI §5.2.** У самого SBOM заполнены creator и timestamp; у компонентов — name, version, координаты (purl/CPE), distribution licences ([[05 Нормативка/BSI TR-03183-2 v2.1.0]]).
- [ ] **Версия формата соответствует норме.** CycloneDX ≥ 1.6 или SPDX ≥ 3.0.1; устаревшие версии формата не принимаются как актуальный evidence.
- [ ] **SBOM не содержит сведений об уязвимостях.** Блока `vulnerabilities` в SBOM нет (BSI §8.1.14 — `MUST NOT`); vuln-данные вынесены в отдельный артефакт.
- [ ] **Динамическая часть выделена отдельно.** Есть VEX/CSAF/VDR, и каждый вердикт ссылается на конкретную версию/purl компонента из SBOM; у VEX указан issuer, evidence и срок пересмотра ([[02 Справочник/VEX в процессе РБПО - откуда берется и как выпускать|VEX в процессе РБПО]], [[03 Практикум/П09. VDR и VEX различие факта и решения|П09]]).
- [ ] **Класс SBOM соответствует объекту.** Для C/C++ — Build SBOM (по линковщику, не Source), для контейнеров — учтены слои (BSI §8.4).
- [ ] **У каждого артефакта есть владелец (роль, не ФИО) и место хранения.** Audit trail централизован и доступен аудитору ([[08 Шаблоны/Журналирование и audit trail|Журналирование и audit trail]]).
- [ ] **Артефакты воспроизводимы.** Для любой строки матрицы описана процедура получить тот же артефакт на следующем релизе; зафиксированы инструмент и его версия.
- [ ] **Исключения и принятие риска трассируемы.** Каждое исключение имеет обоснование, владельца и срок пересмотра ([[03 Практикум/П30. Исключения и принятие риска|П30]]).
- [ ] **Маппинг на стандарты не выдаёт 1:1 за эквивалентность.** В матрице явно отмечено, где у требования нет аналога в смежном стандарте; ID практик SSDF помечены как сверяемые с официальным источником.
