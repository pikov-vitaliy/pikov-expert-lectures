# План занятия (90 минут)

## Цели
К концу занятия слушатель умеет:
1. объяснить, почему `#include` не равен зависимости и где между исходником и бинарём теряется информация о компоненте;
2. отличить динамическую линковку (`.so`, `DT_NEEDED`) от статической (`.a`, слепая зона) и снять обе картины инструментами `ldd`/`readelf`;
3. смаппить динамические библиотеки на DEB-пакеты через `apt`/`dpkg -S` и получить координаты (PURL);
4. оценить, чего не хватает в сыром `cdxgen` SBOM для C/C++, и сформулировать, что должен дозаполнить build-scan и ручная разметка.

## Материалы и подготовка
- Стенд: Debian-based окружение (см. [[П01. Стенд WSL2 Docker и базовая гигиена]]), установленные `gcc`, `binutils` (`readelf`, `objdump`), `cmake`, `cdxgen`; по возможности `conan`.
- Тестовый C++ проект, линкующийся с OpenSSL/zlib двумя способами: динамически и статически.
- Заметки справочника: [[06 C C++ legacy/ELF и разделы dynamic|ELF и DT_NEEDED]], [[06 C C++ legacy/статическая линковка|статическая линковка]], [[06 C C++ legacy/dpkg apt metadata|dpkg/apt metadata]].
- Шаблон: [[08 Шаблоны/Реестр unresolved libraries|Реестр unresolved libraries]].

## Демонстрация (опорные команды)
```bash
make VERBOSE=1            # видим строки линковки (-lssl -lcrypto / -l:libssl.a)
readelf -d ./app | grep NEEDED
ldd ./app
dpkg -S /usr/lib/x86_64-linux-gnu/libssl.so.3
cdxgen -t cpp -o cdxgen-bom.json .
```

## Контрольная точка
Слушатель на своём бинаре показывает: какие зависимости видны через `DT_NEEDED`, какие смаппились на DEB-пакеты, и какие компоненты остаются слепой зоной (статика/vendored/unresolved) — то есть отделяет доказанный факт от того, что требует build-scan или ручной разметки.

> [!tip] Темп
> Если группа слабее в Linux-инструментах, сократите Conan и расширьте блок `readelf`/`dpkg`: главное — чтобы каждый своими руками увидел разницу между динамикой и статикой на одном и том же проекте.
