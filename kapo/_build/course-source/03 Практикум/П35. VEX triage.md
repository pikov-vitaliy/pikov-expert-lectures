# П35. VEX triage

> [!info] Контекст практики
> [[П09. VDR и VEX различие факта и решения]] учит оформить **одно** решение. Здесь задача другая — провести триаж **всего потока** находок и сделать так, чтобы решения не лежали в текстовом файле, а *машинно вычитались* сканером: помеченные `not_affected` находки исчезают из выдачи, и gate перестаёт падать на разобранном шуме. Инструмент — OpenVEX `vexctl` (минимальный, формат-агностичный). Контролируемый результат — OpenVEX-документ, после применения которого число findings у сканера снижается ровно на разобранные CVE. Перед практикой прочитайте [[02 Справочник/VEX в процессе РБПО - откуда берется и как выпускать|VEX в процессе РБПО]].

## Цель

По VDR из 5–10 находок:
- разнести каждую находку по статусу OpenVEX: `not_affected` / `affected` / `fixed` / `under_investigation`;
- для каждого `not_affected` указать обязательный `justification` из разрешённого перечня;
- указать `author`/issuer, который вправе выпускать VEX для этой версии продукта;
- собрать валидный OpenVEX-документ через `vexctl create`;
- применить его к выводу сканера так, чтобы разобранные `not_affected` находки **ушли из отчёта**, а `affected` — остались.

Проверяемый результат: число findings до триажа > числа findings после применения VEX, и разница равна количеству `not_affected`-записей.

## Команда или действие

OpenVEX через `vexctl` (Go-инструмент проекта OpenVEX):

```bash
# 1. Исходный поток находок (тот же SBOM, что и в gate)
grype sbom:sbom.cdx.json -o table | tee before.txt

# 2. Решение по одной находке -> запись OpenVEX
vexctl create \
  --product "pkg:npm/myapp@1.0.0" \
  --subcomponent "pkg:npm/semver@7.3.7" \
  --vuln "CVE-2022-25883" \
  --status "not_affected" \
  --justification "vulnerable_code_not_in_execute_path" \
  --status-note "semver используется только на build-time, в рантайме недостижим" \
  > vex.openvex.json

# (повторить для остальных находок; статусы affected/fixed/under_investigation
#  объединить в один документ через несколько --vuln или vexctl merge)
# Проверьте, что author/issuer в итоговом документе отражает Product Security/PSIRT/AppSec,
# а не имя сканера или внешней базы уязвимостей.

# 3. Применить VEX при сканировании: not_affected уходят из отчёта
grype sbom:sbom.cdx.json --vex vex.openvex.json -o table | tee after.txt
```

Разрешённые `justification` для `not_affected` (OpenVEX): `component_not_present`, `vulnerable_code_not_present`, `vulnerable_code_not_in_execute_path`, `vulnerable_code_cannot_be_controlled_by_adversary`, `inline_mitigations_already_exist`.

## Что вы должны увидеть

Скелет OpenVEX-документа (`vex.openvex.json`):

```json
{
  "@context": "https://openvex.dev/ns/v0.2.0",
  "@id": "https://openvex.dev/docs/public/vex-...",
  "author": "AppSec / Организация",
  "timestamp": "2026-06-18T10:00:00Z",
  "statements": [
    {
      "vulnerability": { "name": "CVE-2022-25883" },
      "products": [
        { "@id": "pkg:npm/myapp@1.0.0",
          "subcomponents": [ { "@id": "pkg:npm/semver@7.3.7" } ] }
      ],
      "status": "not_affected",
      "justification": "vulnerable_code_not_in_execute_path"
    }
  ]
}
```

Эффект применения — число findings падает:

```
# before.txt:  4 findings (CVE-2022-25883 High, CVE-... ...)
# after.txt:   3 findings  <- CVE-2022-25883 отфильтрована как not_affected
```

Признак готовности: `diff` между `before.txt` и `after.txt` показывает ровно те CVE, которые вы пометили `not_affected`; `affected`/`under_investigation` остались в отчёте; gate в CI после VEX перестал падать на разобранном шуме, но продолжает падать на нетриажированных `affected`.

> [!warning] VEX не «глушит» уязвимость — он документирует решение
> `not_affected` без `justification` из перечня — невалидная запись: `vexctl` либо отклонит её, либо она не отфильтрует находку. VEX без `author`/issuer и evidence — слабое управленческое утверждение. И помните: фильтрация работает, только если PURL в `subcomponents` точно совпадает с координатой компонента в SBOM. Несовпадение PURL = VEX «висит в воздухе», находка остаётся.

## Если не получилось

- **`after.txt` равен `before.txt` — ничего не отфильтровалось.** PURL в VEX не совпал с PURL компонента в SBOM (версия, namespace, qualifiers). Сверьте: `jq '.components[] | select(.name=="semver") | .purl' sbom.cdx.json` и тот же ref в VEX.
- **`vexctl: invalid justification`.** Использован `justification` не из перечня OpenVEX (например, скопирован из CycloneDX-словаря — там другие значения, см. [[П09. VDR и VEX различие факта и решения]]). Возьмите значение из списка выше.
- **`author` заполнен внешним источником.** NVD, БДУ, OSV, GHSA и upstream advisory не являются issuer вашего VEX. Их можно указать как evidence, но итоговое утверждение выпускает ответственная за продукт сторона.
- **Отфильтровались `affected`-находки.** Неверный `status`: фильтр снимает только `not_affected` и `fixed`. Проверьте, что эксплуатируемые находки помечены `affected`, а не ошибочно `not_affected`.
- **Документ невалиден / `vexctl` молчит.** Нет обязательных полей верхнего уровня (`@context`, `author`, `timestamp`) или пустой `statements`. Проверьте `jq . vex.openvex.json` и наличие хотя бы одного statement.

## Критерий зачёта

Показать преподавателю: (1) VDR из 5–10 находок и таблицу триажа со статусом, issuer/владельцем и evidence по каждой; (2) валидный OpenVEX-документ с `author` и `justification` из перечня для всех `not_affected`; (3) `before.txt`/`after.txt`, где разница findings = числу `not_affected`; (4) пояснение, чем эта практика отличается от [[П09. VDR и VEX различие факта и решения]] (там — одно решение, здесь — машинно применяемый триаж потока и срок пересмотра `not_affected`).
