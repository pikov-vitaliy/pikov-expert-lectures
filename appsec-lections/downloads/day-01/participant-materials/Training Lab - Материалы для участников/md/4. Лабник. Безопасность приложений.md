# **Правила проведения лабораторных работ**

## **0. Ключевые правила**

* Тестировать методики только в учебной среде, предоставленной для лабораторных работ.
* Не использовать содержимое запросов (payload) и изученные методы против реальных систем.
* Если что-то сломалось, обновите страницу, перезапустите контейнер или откройте новую инкогнито‑сессию.

## **1. Что нужно предоставить в качестве решения**

Для каждой лабораторной работы фиксируйте:

* Скриншот с решённой задачей (таблицу результатов) или иной явный индикатор успеха.
* Ключевой артефакт: ссылку URL, состояние страницы, фрагмент запроса/ответа, конфигурацию или содержимое файла.
* Заполните «Шаблон решения».

## **2. Среда для выполнения лабораторных работ (OWASP Juice Shop\*)**

1. Запустите приложение только через канонический Compose-файл `appsec-lections/lab/juice-shop/compose.yaml`:

```powershell
.\start.ps1
```

1. Откройте в браузере: <http://localhost:3000>

**Рекомендация:** каждый студент запускает собственный экземпляр – так проще сбрасывать состояние и избегать взаимных помех.

\*Это программное обеспечение распространяется бесплатно: вы можете распространять и/или модифицировать его в соответствии с условиями лицензии MIT. OWASP Juice Shop и все вклады защищены авторским правом Bjoern Kimminich и участников проекта 2014‑2021.

## **3. Индекс лабораторных работ (соответствие OWASP Top 10)**

Мы следуем порядку OWASP Top 10 (2025) от A01 до A10.

Подготовительная (нулевая) лабораторная работа формирует обзор активов приложения, после чего переходим к каждому пункту поочерёдно.

## **4. Формат лабораторного занятия (как работать со студентами на занятиях)**

Каждая лаборатория проходит в одинаковом ритме, чтобы курс оставался ориентированным на концепции, а не на инструменты.

* **Контекст** (5–7 мин): определение категории + реальный сценарий – объясняется во время презентации.
* **Выполнение лабораторной работы** (20–25 мин): следуем списку шагов и фиксируем доказательства.
* **Разбор** (10–12 мин): коренная причина → паттерн профилактики → план верификации.

# **ЛР\_0 — Инвентаризация активов и критические активы (поиск в Juice‑Shop)**

*Подготовительная лабораторная работа охватывает активы, точки входа и границы доверия.*

## **Цели**

* Выявить активы (данные + функциональность) и ранжировать их по критичности.
* Определить точки входа и границы доверия.
* Сформулировать топ‑5 критических активов, которые необходимо защищать в течение жизненного цикла разработки (SDLC).

## **Шаги**

1. Пройдитесь по приложению и просмотрите каталог товаров → зарегистрируйтесь → войдите в систему → добавьте товары в корзину → откройте страницы оформления/оплаты → зайдите в раздел «About/Contact».
2. Составьте инвентарь активов, включив:
   1. Идентификации/роли,
   2. Сессии/токены,
   3. Заказы/корзину,
   4. Процесс оплаты,
   5. Административные функции,
   6. Файлы/загрузки,
   7. API,
   8. Телеметрию/метрики/логи.
3. Сопоставьте точки входа: UI‑маршруты, REST‑эндпоинты (`/api`, `/rest`), файловые эндпоинты (например, `/ftp`), всё, что можно обнаружить через клиентский JavaScript.
4. Определите границы доверия: Браузер ↔ Веб‑приложение; Веб‑приложение ↔ База данных; Веб‑приложение ↔ Сторонние сервисы; потоки только для администраторов ↔ обычных пользователей.
5. Выберите «Топ‑5 критических активов» и опишите, каковы последствия их компрометации

# **ЛР\_1 — Пакет контроля доступа**

*Лабораторная работа охватывает первый риск OWASP Top 10:2025 A01 — Нарушение контроля доступа.*

## **Часть 1 — Поиск административного маршрута (концепция вертикального контроля доступа)**

**Шаги**

1. Откройте «DevTools → Sources».
2. Поищите какие из файлов приложения могут быть полезны для определения скрытых ресурсов
3. Используя файлы или иным способом найдите административные ресурсы приложения, инвентаризируйте их и попробуйте получить доступ
4. Зафиксируйте поведение и сделайте скриншот.

## **Часть 2 — Просмотр корзины другого пользователя (горизонтальный контроль доступа / IDOR)**

**Шаги**

1. Войдите в систему как обычный пользователь и добавьте 1‑2 товара в корзину.
2. Откройте «DevTools → Application (Storage).
3. Найдите переменную, отвечающую за идентификатор корзины.
4. Проверьте наличие валидации доступа к существующим «корзинам» и попробуйте получить доступ к корзине другого пользователя.
5. При необходимости выполните «жёсткое» обновление страницы.
6. Зафиксируйте доказательство доступа к чужой корзине (или скриншот решённого задания в таблице результатов).

## **Вопросы для обсуждения**

* Где обязательно должна происходить авторизация (пользовательский интерфейс (UI), интерфейс программирования приложений (API), база данных)?
* Какие идентификаторы сервер никогда не должен принимать от клиента как достоверные?

## **Список проверок для предотвращения**

* Выполнять проверку авторизации на сервере для каждого объекта (проверка владения).
* Избегать прямых ссылок на объекты без авторизации.
* Предпочитать случайные (opaque) идентификаторы, чтобы снизить предсказуемость.

Откройте несуществующий REST‑эндпоинт и посмотрите, возвращает ли сервер подробные сообщения об ошибке:

## **Список проверок для предотвращения**

* Удалять неиспользуемые/устаревшие эндпоинты; применять списки разрешённых путей на границе (gateway/WAF — последний уровень защиты).

# **ЛР\_4 — Утечка конфиденциальных документов через публичный файловый раздел + неподписанный JWT**

*Лабораторная работа охватывает четвёртый риск OWASP Top 10:2025 A04 — Криптографические уязвимости (рассматривается как утечка чувствительных данных и отсутствие защиты).*

## **Часть 1 – Утечка конфиденциальных документов через публичный файловый раздел**

### **Шаги**

1. В пользовательском интерфейсе откройте раздел «About Us» и найдите ссылку «Terms of Use» (она ведёт в каталог `/ftp`).
2. Откройте листинг FTP‑каталога
3. Ищите конфиденциальные/внутренние документы. Попробуйте открыть такой файл.
4. Зафиксируйте доказательство и убедитесь, что соответствующее задание отмечено как выполненное (если оно присутствует в вашей таблице результатов).

## **Вопросы для обсуждения**

* Почему это нельзя назвать просто «неправильной конфигурацией»? Какой уровень классификации данных был нарушен?
* Когда следует использовать шифрование, а когда достаточно контроля доступа?

### **Список проверок для предотвращения**

* Не раскрывать внутренние файловые области неаутентифицированным пользователям.
* Классифицировать данные и применять явные политики доступа.
* Отключить листинг каталогов / авто‑индексацию.

## **Часть 2 – Неподписанный JWT-токен**

### **Шаги**

1. Войдите в систему под любой учётной записью.
2. Найдите JWT‑токен, используемый приложением для идентификации пользователя
3. Декодируйте заголовок и полезную нагрузку токена (base64url).
4. Проверьте проверяет ли сервер алгоритм подписи и саму подпись токена. Если проблема обнаружена, попробуйте модифицировать одно из полей для получения привилегированного доступа.
5. Повторно закодируйте заголовок и полезную нагрузку в base64url.
6. Используйте полученный токен в запросе и зафиксируйте результат (привилегированное поведение или решение задания).

### **Список проверок для предотвращения**

* Отклонять токены с `alg=none`; требовать подписи и фиксировать разрешённые алгоритмы.
* Проверять `issuer`, `audience`, срок действия и подпись с использованием корректных ключей.

## **Часть 1 — SQL‑инъекция при входе (обход аутентификации)**

# **ЛР\_11 — Инъекция команд через переполнение буфера (коррупция данных → выполнение команд)**

Лабораторная работа охватывает влияние повреждения памяти и отвечает на вопрос, почему сочетание shell-вызова и влияния атакующего опасно. Касается темы «Безопасность памяти и риски нативного кода».

**Режим текущего пакета:** только статический code review. Сборка и запуск намеренно уязвимого примера запрещены, пока преподаватель не предоставил отдельный одноразовый runner без сети, с лимитами процессов/памяти/CPU и автоматической очисткой.

**Примечание к области**: В этой лаборатории намеренно не используется эксплуатация управления потоком (ROP/ret2libc). Цель — показать, как переполнение может привести к выполнению команд, повреждая соседние данные.

## **Цели**

* Понять разницу между классической инъекцией команд и выполнением команд, вызванным переполнением памяти.
* Объяснить гипотетическую цепочку «выход за границу → изменение соседних данных → опасный sink», не выполняя её.
* Исправить первопричину (границы) и убрать влияние атакующего на выполнение команды.
* Составить короткий список профилактических мер и план верификации для реальных проектов.

## **Модель угроз**

* **Ввод атакующего**: длинная строка, подаваемая туда, где программа ожидает имя.
* **Нарушенное предположение**: строка команды считается «внутренней», но размещена рядом с пользовательским буфером.
* **Последствия**: команда, исполняемая оболочкой ОС, может быть заменена на произвольную, выбранную атакующим.

## **Часть 1 — Статический разбор**

|  |  |
| --- | --- |
| **Команда** | **Описание** |
| `cmd\_vuln` | найти неверную границу чтения и опасный sink; не собирать |
| `cmd\_fixed` | сравнить границу `sizeof` и отсутствие shell-вызова |

В текущем пакете выполнение отключено:

```bash

echo "CODE-REVIEW-ONLY: executable fixture is not distributed"

```

**Ожидаемый результат**: только приведённая выше строка; исполняемый файл отсутствует.

## **Часть 2 — Моделирование без payload**

На схеме отметьте 64-байтовую границу `name`, соседнее поле и sink. Не создавайте строку переполнения и не подставляйте команду ОС.

```bash

PAYLOAD НЕ ВЫПОЛНЯЕТСЯ: опишите ожидаемое повреждение на бумаге

```

* Зафиксируйте data-flow и нарушенную границу как текстовое доказательство.
* Предложите отрицательный тест для будущего изолированного runner.

## **Часть 3 — Проверка исправления**

```bash

ПРОВЕРКА ДИЗАЙНА: fgets(name, sizeof(name), stdin) и отсутствие shell-вызова

```

**Ожидаемый результат:** ввод ограничен размером буфера, а выполнение команд ОС отсутствует.

## **Вопросы для обсуждения**

* Почему это всё равно «инъекция команд», хотя ввод не конкатенируется напрямую со строкой команды?
* Что является основной уязвимостью: опасный shell-вызов или переполнение буфера? Почему защита требует устранить оба элемента цепочки?
* Каков был бы реальный риск, если такой код был доступен по сети (например, в виде демона/службы)?

## **Список проверок для предотвращения**

* По возможности использовать языки с безопасной обработкой памяти (memory safe languages).
* Всегда задавать корректные границы для функций ввода (например, `fgets` с `sizeof`, проверка длины).
* Не размещать чувствительные данные рядом с пользовательскими буферами в памяти (уменьшить риск «смежных переменных»).
* Избегать интерпретации оболочки; предпочтительно использовать семейство `exec` с фиксированным массивом аргументов (или полностью убрать выполнение команд ОС).
* Компилировать с включёнными механизмами защиты (stack protector, PIE, RELRO, FORTIFY) и запускать сборки с санитайзерами в CI.
* Добавлять тесты границ и фаззинг для нативных парсеров и обработчиков протоколов.

## **Исходный код**

### **`overflow\_cmd.c` — неисполняемый фрагмент для code review**

```text

#include <stdio.h>

#include <string.h>

#include <stdlib.h>

/\*

\_INTENTIONALLY VULNERABLE (TRAINING ONLY)\_

\_DATA‑ORIENTED exploit demo:\_

- пользовательский ввод попадает в name[64]

- переполнение затрагивает соседний cmd[64]

- cmd затем дошёл бы до shell sink; вызов в этом материале заменён несуществующим маркером

NOTE: демонстрируется без эксплуатации управления потоком (ROP/ret2libc).

\*/

typedef struct {

char name[64];

char cmd[64];

} Frame;

int main(void) {

Frame f;

memset(&f, 0, sizeof(f));

/\* базовая безопасная команда \*/

strcpy(f.cmd, "echo SAFE\_COMMAND");

puts("overflow\_cmd: enter your name:");

puts("(Hint: long input can corrupt adjacent variables)");

/\* VULNERABLE: читает до 1023 байт в буфер из 64 байт → переполняет f.cmd \*/

if (fgets(f.name, 1024, stdin) == NULL) {

puts("Input error.");

return 1;

}

/\* удаляем перевод строки \*/

f.name[strcspn(f.name, "\n")] = '\0';

/\* если переполнение записало перевод строки в cmd, отрезаем его \*/

f.cmd[strcspn(f.cmd, "\n")] = '\0';

printf("Hello, %s\n", f.name);

printf("About to run: [%s]\n", f.cmd);

/\* опасно в реальных приложениях: выполнение оболочки с данными, контролируемыми атакующим \*/

EXECUTION_DISABLED(f.cmd); /* намеренно не компилируется и не исполняет shell */

return 0;

}

```

### **`overflow\_cmd\_fixed.c` — исправленная версия** (корректные границы, отсутствие влияния атакующего)

```c

#include <stdio.h>

#include <string.h>

#include <stdlib.h>

/\*

\_FIXED VERSION\_

\_Исправлено переполнение и убрано влияние атакующего на выполняемую команду:\_

- ввод читается с правильными границами (sizeof)

- выполнение команд ОС полностью удалено

\*/

int main(void) {

char name[64];

puts("overflow\_cmd\_fixed: enter your name:");

if (fgets(name, sizeof(name), stdin) == NULL) {

puts("Input error.");

return 1;

}

name[strcspn(name, "\n")] = '\0';

printf("Hello, %s\n", name);

/\* shell-вызов отсутствует \*/

puts("SAFE\_COMMAND");

return 0;

}

```

### **Сборка**

Сборочные цели намеренно не распространяются. Для практического запуска нужен отдельный проверенный runner с `--network none`, удалёнными capabilities, `no-new-privileges`, лимитами ресурсов, непривилегированным UID и гарантированной очисткой.
