Участники: Виталий Пиков

Полные риски при обработке данных
Виталий Пиков обсуждает риски, связанные с обработкой данных, включая передачу файлов через защищённые каналы, возможные атаки типа 'подмена порта' или 'выполнение кода на сервере'. Приводятся примеры уязвимых сценариев, где загрузка файлов может привести к утечке данных или несанкционированному доступу. Упоминается необходимость проверки целостности данных и контроль доступа.

Разбор 13 категорий уязвимостей
Начало обсуждения 13 категорий уязвимостей из проекта OWASP Top 10. Первая категория — 'Нарушение контроля доступа', объясняемая через примеры из интернет-магазинов. Рассматриваются случаи, когда аутентифицированный пользователь получает доступ к чужим данным (например, корзинам) из-за отсутствия проверки прав. Приводится пример SQL-запроса, где изменение ID позволяет получить чужие данные.

Безопасность конфигурации серверов
Обсуждение второй категории — 'Уязвимости конфигурации'. Примеры включают устаревшие API-интерфейсы, незащищённые секреты в Kubernetes и некорректные настройки веб-серверов (например, вывод стека вызовов при ошибке). Подчёркивается важность минимализма в конфигурациях и регулярного аудита инфраструктуры.

Атаки цепочки поставок ПО
Третья категория — 'Уязвимости цепочки поставок'. Рассматриваются случаи компрометации библиотек через: 1) опечатки в названиях пакетов (пример: 'kbank' vs 'keba'), 2) взлом аккаунтов разработчиков и публикация вредоносных версий (как в случае библиотеки 'acme'). Обсуждаются методы защиты: фиксированные версии зависимостей, воспроизводимые сборки и внутренние реестры.

Лабораторная работа №1-3
Старт практической части: студентам предлагается выполнить три задания. Первое — найти уязвимость в API корзины (IDOR), второе — обнаружить уязвимую библиотеку в зависимостях, третье — протестировать JWT-токены на слабые алгоритмы подписи. Указаны временные рамки (15 минут) и критерии оценки.

Классификация уязвимостей по ГОСТ
Дискуссия о терминологии: различие между 'дефектом' и 'уязвимостью' согласно ГОСТ 56939-2022. Подчёркивается, что уязвимость — это дефект, способный привести к реальной угрозе. Приводится пример кнопки без обработчика событий как 'дефекта', но не уязвимости.

JWT-токены и CSRF-защита
Объяснение уязвимостей в JWT: 1) использование слабых алгоритмов подписи (None, HS256), 2) отсутствие проверки полей 'exp' и 'nbf'. Методы защиты: обязательный HTTPS, строгий контроль сроков жизни токенов, SameSite-флаги кук. Практическое задание — попытаться изменить claims токена вручную.

Открытые перенаправления (Open Redirect)
Четвёртая категория уязвимостей: примеры опасных перенаправлений (например, через параметр URL). Методология защиты: 1) использование белых списков доменов, 2) проверка реферера, 3) избегание прямого передачи URL-параметров. Практическая демонстрация атаки через поддельный домен.

Инъекция команд (OS Command Injection)
Пятая категория: примеры атак через передачу параметров в shell-команды (например, через HTTP-заголовки). Защитные меры: 1) полный отказ от вызова внешних команд, 2) белый список допустимых символов, 3) sandbox-окружение. Практическое задание — попытаться выполнить произвольную команду через уязвимый API.

Безопасность ИИ и LLM
Заключительная часть: обсуждение рисков, связанных с использованием LLM (Large Language Models). Основные угрозы: 1) утечки данных через prompt-injection, 2) генерация вредоносного кода, 3) манипуляции через jailbreak-атаки. Рекомендации: 1) изоляция контекстов, 2) аудит выходных данных, 3) использование sandbox-режимов. Упоминается новый стандарт NIST AI RMF для безопасной интеграции ИИ.

Разработка стандартов безопасности ИИ
Виталий Пиков обсуждает текущую разработку национального стандарта "Безопасная разработка систем с искусственным интеллектом", упоминает участие команды в его создании через деятельность Комитета по стандартам. Отмечает связь этого процесса с более широким контекстом регулирования ИИ-технологий.

Скорость разработки из-за праздников
Замечено ускорение процессов разработки из-за праздничных периодов, но при этом остаются нерешённые задачи. Упоминается необходимость подготовки учебной программы для специалистов, работающей с ИИ-системами, включая актуализацию материалов и использование генератора контента.

Проверка обучающих данных ИИ
Обсуждается механизм проверки обучающих данных модели ИИ на наличие опасных комбинаций информации. Подчёркивается важность контроля за тем, чтобы отдельные элементы данных, кажущиеся безопасными по отдельности, не создавали проблемные комбинации при обучении системы. Также отмечается проблема быстрого устаревания обучающих наборов данных.

Автоматическое обновление знаний ИИ
Описывается система автоматического обновления базы знаний ИИ через анализ веб-страниц и корректировку моделей на основе новых данных. Приводится пример интерфейса, где система предупреждает о потенциальных рисках в генерируемом коде, демонстрируя принцип работы механизмов безопасности ИИ.
