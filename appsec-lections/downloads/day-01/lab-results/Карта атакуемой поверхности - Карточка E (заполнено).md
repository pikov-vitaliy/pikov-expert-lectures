# Карта атакуемой поверхности — Карточка Е

**Страница / экран:** Juice Shop — Customer Complaint / Обратная связь (`/#/complain`)
**Группа / приложение:** OWASP Juice Shop

---

## 1. Точки входа

*Поля, кнопки/действия, параметры URL, скрытые поля, запросы к API, загрузка файлов, куки-файлы/токены, сторонние виджеты.*

- **Текстовое поле** — сообщение (comment). Отображается без sanitization — HTML-теги рендерятся → XSS.
- **Загрузка файла** — поле вложения (invoice). Принимает `.pdf`, `.zip`.
- **API: `POST /api/Complaints`** — требует авторизацию (JWT), принимает JSON с текстом и файлом.
- **API: `POST /api/Feedbacks`** — без авторизации (UserId = null), но требует `captchaId` и ответ капчи.
- **API: `POST /file-upload`** — принимает multipart/form-data, возвращает 204. Точка входа для загрузки.
- **Скрытый параметр: `captchaId`** — обязателен для `/api/Feedbacks`. Проверяется на сервере.
- **Параметр: `UserId`** — можно подставить чужой → forged feedback.
- **Параметр: `rating`** — целое число. Клиент не даёт поставить 0, сервер принимает 0 → zeroStarsChallenge.
- **Заголовок: Authorization (JWT)** — нужен для `/api/Complaints`, опционален для `/api/Feedbacks`.
- **Структурированные файлы: XML** — сервер парсит XML внутри загруженных файлов → XXE (чтение `/etc/passwd`, DoS).
- **Структурированные файлы: YAML** — сервер парсит YAML → YAML-бомба (Billion Laughs, memory exhaustion).
- **Устаревший, но доступный путь загрузки** — старый endpoint (возможно, `/ftp/` или загрузка аватара `/profile`), до сих пор принимает файлы в обход новых проверок.
- **Токен сессии в куки-файлах / заголовках** — определяет, от чьего имени отправляется обращение.

## 2. Активы: данные и функции

*Отдельно ценные данные и отдельно ценные функции этого экрана.*

**Данные:**
- Обращения пользователей (комментарии, рейтинги) — доступны всем через `GET /api/Feedbacks`
- Привязка обращения к UserId — персональные данные
- Загруженные файлы (счета, документы) — хранятся на сервере
- Системные файлы сервера (`/etc/passwd`, `C:\Windows\system.ini`) — достижимы через XXE


**Функции:**
- Отправка жалобы / обратной связи
- Загрузка и хранение вложений
- Парсинг структурированных файлов (XML, YAML)
- Просмотр всех отзывов (GET `/api/Feedbacks`)
- Удаление отзывов (feedbackChallenge)

## 3. Роли и границы доверия

*Кто легитимно пользуется экраном; где граница браузер <-> сервер <-> БД; что приходит от клиента.*

**Роли:**
- **Аноним** (без авторизации) — может отправлять feedback, просматривать все отзывы
- **Авторизованный пользователь** — может отправлять complaints с вложениями
- **Администратор** — просматривает все обращения (потенциальная жертва XSS)

**Границы доверия:**

| Граница | Что переходит | Почему нельзя верить |
|---------|---------------|---------------------|
| Браузер → Сервер | `comment`, `rating`, файл | Всему: comment — XSS, rating не валидирован, файл — любой |
| Браузер → Сервер | `UserId` в теле запроса | Клиент может подставить любой |
| Браузер → Сервер | `captchaId`, ответ капчи | Автоматизируется (10 отзывов за 20 сек) |
| Сервер → XML-парсер | Содержимое файла | Внешние сущности (XXE) |
| Сервер → YAML-парсер | Содержимое файла | Якоря-бомбы (Billion Laughs) |
| Сервер → Файловая система | Имя файла | Null-байт, двойное расширение — обход `.pdf`/`.zip` |

## 4. Возможные злоупотребления

*По каждой значимой точке входа: «действующее лицо → действие → нежелательный эффект».*

| # | Линза | Сценарий |
|---|-------|----------|
| 1 | Чужой объект | Пользователь → подставляет чужой `UserId` в `POST /api/Feedbacks` → пишет отзыв от имени другого |
| 2 | Чужой объект | Пользователь → подставляет чужой `id` в `GET /api/Feedbacks/N` → читает чужие обращения |
| 3 | Не тот, за кого себя выдаёт | Аноним → вызывает `POST /api/Complaints` без токена → получает доступ к защищённому функционалу |
| 4 | Ввод, который станет кодом | Злоумышленник → вводит `<script>alert(1)</script>` в comment → XSS у админа при просмотре |
| 5 | Ввод, который станет кодом | Злоумышленник → загружает XML с `<!ENTITY xxe SYSTEM "file:///etc/passwd">` → читает системный файл |
| 6 | Ввод, который станет кодом | Злоумышленник → загружает XML с `/dev/urandom` как внешнюю сущность → сервер зависает |
| 7 | Ввод, который станет кодом | Злоумышленник → загружает YAML-бомбу (Billion Laughs) → парсер падает по памяти |
| 8 | Клиенту верить нельзя | Злоумышленник → отправляет `rating: 0` в обход интерфейса → нулевой рейтинг сохранён |
| 9 | Клиенту верить нельзя | Злоумышленник → загружает `.exe` через перехват запроса → сервер принимает не-PDF/ZIP |
| 10 | Клиенту верить нельзя | Злоумышленник → загружает файл > 100 kB → сервер принимает слишком большой файл |
| 11 | Забытое и лишнее | Злоумышленник → находит старый endpoint загрузки → обходит проверки нового механизма |
| 12 | Забытое и лишнее | Злоумышленник → использует null-байт в имени: `file.pdf%00.exe` → обход проверки расширения |

## 5. Топ-1 риск и первая защита

*Самый опасный сценарий + одна серверная мера, которая его закрывает.*

**Риск:** XXE-инъекция через загруженный XML-файл — злоумышленник читает `/etc/passwd` и другие системные файлы, а также может вызвать отказ в обслуживании (XXE DoS).

**Первая защита:** Отключить обработку внешних сущностей (DTD) в XML-парсере на сервере:

```
parser.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)
parser.setFeature("http://xml.org/sax/features/external-general-entities", false)
parser.setFeature("http://xml.org/sax/features/external-parameter-entities", false)
```

А также полностью отказаться от парсинга структурированных форматов (XML, YAML) из непроверенных источников, либо использовать безопасные парсеры: `defusedxml` (Python), `DefusedXML` (Node.js).
