## ЛР_1 — Пакет контроля доступа (A01)

### Часть 1 — Поиск административного маршрута (вертикальный контроль доступа)

**Что сделано:**
В файле main.js найден скрытый маршрут `/#/administration` с защитой `canActivate`. Обычный пользователь (labuser@test.com) смог получить список всех пользователей через `GET /api/Users` — сервер не проверяет роль в запросе.

**Доказательства:**
- Маршрут `/#/administration` найден в main.js: `path:"administration"` c `canActivate:[ss]`
- `GET /api/Users` от имени labuser вернул данные всех 24 пользователей (включая admin)
- `GET /rest/admin/application-configuration` — полная конфигурация приложения доступна обычному пользователю

**Ключевая причина:**
Сервер не проверяет роль пользователя при доступе к административным API-эндпоинтам. Middleware авторизации отсутствует или не применяется ко всем эндпоинтам.

### Часть 2 — Просмотр корзины другого пользователя (IDOR / горизонтальный контроль доступа)

**Что сделано:**
Пользователь labuser (bid=6) получил доступ к корзине администратора (bid=1) через `GET /rest/basket/1`. Сервер не проверяет принадлежность корзины текущему пользователю.

**Доказательства:**
- `GET /rest/basket/1` от имени labuser вернул корзину админа: 2×Apple Juice, 3×Orange Juice, 1×Eggfruit Juice
- ✅ Флаг **View Basket** получен

**Ключевая причина:**
Отсутствие серверной проверки авторизации для каждого объекта. Сервер доверяет идентификаторам, приходящим от клиента (BasketId), не проверяя принадлежность объекта текущему пользователю.

**Потенциальные последствия:**
- Доступ к чужим заказам и персональным данным
- Доступ к административным функциям (управление пользователями, конфигурацией)
- Утечка чувствительных данных всех пользователей

**Исправление / профилактика:**
- Проверять авторизацию на сервере для каждого объекта (ownership check)
- Не принимать идентификаторы объектов от клиента как достоверные
- Использовать opaque/random идентификаторы вместо предсказуемых
- Middleware авторизации на уровне API с проверкой роли

## ЛР_2 — Устаревший интерфейс (A02)

**Что сделано:**
Обнаружен устаревший (deprecated) endpoint `/file-upload`, отвечающий HTTP 410: *«B2B customer complaints via file upload have been deprecated for security reasons»*. Endpoint принимает файлы любых расширений (не только PDF/ZIP) и пытается парсить их как XML.

**Доказательства:**
- `POST /file-upload` с `test.xml` вернул HTTP 410 с сообщением: *«Failed to parse XML (test.xml)»*
- Стек-трейс: `at handleXmlUpload (/juice-shop/build/routes/fileUpload.js:129:26)`
- ✅ Флаг **Deprecated Interface** получен

**Ключевая причина:**
Неполное удаление устаревшей функциональности. Старый B2B-интерфейс загрузки жалоб был помечен как deprecated, но endpoint остался доступен и не был удалён из маршрутизации.

**Потенциальные последствия:**
- Обход серверных ограничений на типы файлов
- Загрузка вредоносных XML-файлов (XXE-атаки)
- Расширение поверхности атаки через забытые компоненты

**Исправление / профилактика:**
- Полное удаление устаревших endpoint'ов из маршрутизации
- Инвентаризация API-поверхности при каждом релизе
- Серверная валидация файлов по содержимому (magic bytes), а не только по расширению
- Применение allowlist-подхода на API-шлюзе (разрешено только то, что явно указано)

## ЛР_3 — Уязвимая библиотека (A03)

### Часть 1 — Получение забытого резервного файла (Poison Null Byte)

**Что сделано:**
Через обход блокировки расширения с помощью Poison Null Byte (`%2500.md`) получен доступ к файлу `/ftp/package.json.bak`. Прямой доступ (`/ftp/package.json.bak`) возвращал HTTP 403 Forbidden.

**Доказательства:**
- `GET /ftp/package.json.bak%2500.md` вернул содержимое `package.json` (HTTP 200)
- В package.json найдены версии зависимостей: sanitize-html 1.4.2, js-yaml 3.10, libxmljs 0.18, sqlite3 3.1.13
- ✅ Флаг **Forgotten Developer Backup** получен

### Часть 2 — Поиск уязвимой зависимости и сообщение о ней

**Что сделано:**
В package.json.bak обнаружена уязвимая версия `sanitize-html 1.4.2` (CVE-2017-16016 — XSS). Через форму обратной связи отправлен отчёт с указанием конкретной библиотеки, версии и CVE. Решена капча.

**Доказательства:**
- Отчёт отправлен через `POST /api/Feedbacks` с решением капчи
- ✅ Флаг **Vulnerable Library** получен

**Ключевая причина (Ч1):**
Некорректная фильтрация расширений на основе строкового сравнения (только суффикс), не учитывающая null-байт. Сервер интерпретирует `package.json.bak%00.md` как допустимый `.md`-файл.

**Ключевая причина (Ч2):**
Отсутствие SBOM и автоматизированного сканирования зависимостей. Резервная копия package.json с точными версиями библиотек доступна публично.

**Потенциальные последствия:**
- Утечка конфигурации и списка зависимостей приложения
- Эксплуатация известных уязвимостей в устаревших библиотеках (XSS, XXE, Memory Bomb)
- Компрометация сервера через цепочку уязвимостей в зависимостях

**Исправление / профилактика:**
- Генерация SBOM и автоматическое сканирование уязвимостей в CI/CD (npm audit, Snyk, OWASP Dependency-Check)
- Запрет на хранение чувствительных файлов (package.json, .bak, .env) в рабочих каталогах
- Фильтрация файлов на основе содержимого (magic bytes), а не расширения
- Удаление артефактов разработки из production-образов
- Политика своевременного обновления зависимостей (SLA на патчи)
