# ЛР SSRF: закрытый трёхсервисный стенд

## Назначение

Этот fixture демонстрирует SSRF исключительно в локальной учебной сети. Сервис `app` получает URL от клиента и **намеренно небезопасно** выполняет server-side HTTP‑запрос. Сервис `internal` не имеет опубликованного порта и отвечает только синтетической строкой. Локальный `gateway` публикует порт только потому, что Docker Desktop не создаёт host‑binding для сервиса, подключённого исключительно к `internal: true` сети; gateway всегда проксирует запрос к одному фиксированному адресу `app` и не интерпретирует URL из JSON. Это не пример production‑кода и не стенд для проверки реальной сети.

## Границы безопасности

- Порт gateway привязан только к loopback-адресу `127.0.0.1` и выбранному локальному порту (`8080` по умолчанию).
- Уязвимое `app` и `internal` находятся только в Docker‑сети `labnet` с `internal: true`: они не имеют маршрута во внешнюю сеть и не публикуют порты на хост.
- Gateway имеет отдельную техническую bridge‑сеть для host‑binding, но не исполняет пользовательский URL и обращается только к фиксированному `http://app:8080` в `labnet`.
- Для каждого сервиса заданы лимиты PID, памяти и CPU; capabilities удалены, а получение новых привилегий запрещено.
- Единственный разрешённый учебный маршрут — `http://internal:9000/meta`.
- Не вводите внешние URL, IP корпоративной сети, localhost хоста, адреса облачных metadata service или произвольные DNS‑имена.
- Не меняйте compose на `network_mode: host`, не добавляйте привилегии и не подключайте контейнер к другой сети.

## Preflight и запуск

Нужны Docker Engine 28.0.0 или новее и Compose v2. На более старых версиях
Docker порт, привязанный к localhost, мог быть доступен соседям в том же
L2-сегменте; такой движок для уязвимого стенда запрещён. Основание —
[документация Docker о публикации портов](https://docs.docker.com/engine/network/port-publishing/).
Выполняйте только wrapper из этой папки. Он проверяет версию Docker, Compose,
свободный loopback-порт и метки владения всех объектов фиксированного проекта
`appsec-day2-ssrf`. Если обнаружен одноимённый чужой проект, выполнение
останавливается до запуска или удаления каких-либо объектов.

```powershell
.\start.ps1 -LabPort 8080
```

Откройте `http://127.0.0.1:$LabPort/`. Параметр меняет только host‑binding
gateway; порты `app` и `internal` на хост не публикуются. Если preflight
остановился, не продолжайте запуск до устранения причины.

## Разрешённая демонстрация

Отправьте **только** этот запрос в локальный сервис:

```powershell
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:$LabPort/fetch" `
  -ContentType 'application/json' `
  -Body '{"url":"http://internal:9000/meta"}'
```

Ожидаемый результат содержит синтетический маркер `INTERNAL_METADATA=synthetic-lab-value`. Затем в отдельном окне можно зафиксировать след доступа:

```powershell
docker compose --project-name appsec-day2-ssrf -f docker-compose.yml logs internal
```

## Задание

1. Нарисуйте поток «браузер → gateway → app → internal» и отметьте границу доверия.
2. Объясните первопричину: пользователь управляет адресом, по которому запрос выполняет сервер.
3. Сформулируйте исправление: вместо произвольного URL — известный идентификатор ресурса либо строгий allowlist; проверка схемы, имени, фактического IP после DNS и каждого redirect; timeout, лимиты размера/типа; egress policy.
4. Опишите отрицательные тесты и ожидаемый безопасный результат для запрещённого маршрута. Не выполняйте эти тесты против внешних адресов.
5. Покажите, почему сетевое ограничение уменьшает последствия, но не исправляет прикладную первопричину.

## Завершение

После занятия обязательно остановите и удалите учебное состояние только через
ownership-aware wrapper:

```powershell
.\stop.ps1
```

Он сверяет `expert.pikov.lab` и `expert.pikov.config` у каждого контейнера,
network и volume **до** `down`; при коллизии имени чужие объекты остаются
нетронутыми. Если была изменена среда, перед следующим запуском восстановите
исходный compose‑файл из пакета. Не используйте контейнеры этого упражнения в
другой сети.
